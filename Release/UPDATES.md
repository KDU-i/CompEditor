# CompEditor signed in-app updates

Implementation: pinned Sparkle 2.10.0 standard updater, Japanese application-menu and General-settings buttons. The controller remains retained after a manual check. Startup checks availability metadata; application download and installation require the existing manual Sparkle flow. No system profiling, custom query/device identifiers or document sending is added. Normal HTTP activity still exposes IP and client metadata to the feed provider; manual Sparkle requests also send application/Sparkle version metadata. A busy manual session ignores a second request; failed manual checks can be retried. Sparkle handles download cancellation and installation according to stage. Deferred/downloaded updates can persist and may install on a later normal quit; cancellation after staging is not an unconditional discard or rollback guarantee.

Startup availability checks use an ephemeral URLSession with an 8-second wall deadline and resource timeout, a 256 KiB response limit, no shared cookies/credentials/cache, and at most three approved HTTPS redirects. Redirects are limited to the configured repository's appcast locations and GitHub's release-assets CDN path. Only the appcast is fetched, never release notes or an application archive. One attempt is allowed per launch and at most once every 24 hours across launches, including failures; the attempt time is persisted before starting. A backwards clock preserves that limit until the saved attempt plus 24 hours. Invalid configuration/version data, offline failures, HTTP errors, malformed/oversized XML, disallowed redirects and timeout all finish silently. Fetching and parsing occur off the UI actor. A candidate changes only the existing application-menu item's title and update badge, with no dialog, window activation or editing interruption. Opening the menu reveals the notice; a manual check clears it and cancels any startup request.

This startup notice is unverified metadata, not a verified or installable update. It cannot bypass the mandatory Sparkle feed/archive signature checks performed by the manual update flow. Sparkle 2.10.0's public probing API has no cancel or per-probe timeout API, so it cannot provide the short, bounded startup request used here. The separate metadata reader does not reproduce Sparkle's signature protocol or start its installer. Candidate selection requires an explicit valid semantic display version with no prerelease, no channel element, an approved fixed archive whose stable `v` tag matches that version, a newer numeric CFBundleVersion, and no semantic-version downgrade. Minimum/maximum macOS constraints are honored. Same-version higher builds are eligible, including historical release candidates that displayed `0.2.0` but had a lower build number than the formal release.

Fork configuration is separate from CotEditor. The owner-approved dedicated Ed25519 public key is embedded in Info.plist and Release/UpdaterPublicKey.txt. The approved feed is https://github.com/KDU-i/CompEditor/releases/latest/download/appcast.xml; hosting is not published by this change. Do not reuse CotEditor's public key/feed. Empty/invalid configuration never constructs or starts an updater. The production key must be a real approved Ed25519 public key; no secret key, certificate or CI secret belongs in the app or repository.

Allowed feed locations are HTTPS appcast.xml under the selected KDU-i/CompEditor repository (GitHub Release latest appcast, repository main raw appcast, or GitHub Pages /CompEditor/appcast.xml). This list does not create/publish any hosting. Enclosures must use a version-fixed HTTPS GitHub Release ZIP under the same repository. Credentials, query identifiers, fragments, traversal, HTTP, foreign repositories and installer-package items are refused. Require signed feeds with no expiration fallback and archive verification before extraction. Sparkle validates actual signatures; the host does not implement a second crypto protocol.

Updates are not offered for installation while documents are unsaved. If editing begins during download, relaunch is postponed. Save/close documents, then the same update button resumes the prepared installer. Standard Sparkle/Cocoa termination remains in place; the host never force-quits or overwrites a running app. A failed or canceled pre-install check/download leaves the existing app. No automatic rollback after installation is promised.

Version rules: CFBundleShortVersionString 0.2.0, formal CFBundleVersion 856; published rc.2 uses 855, rc.1 uses 854 and earlier artifacts used 853. Future build numbers must increase. Build 856 uses the formal v0.2.0 fixed archive URL and matching source assets. Existing rc tags and application bytes remain unchanged. Older versions without the updater need one manual installation first. The configured candidate can check its approved feed manually once hosting is published.

A dedicated key was generated with the official Sparkle tool under owner approval and remains in the Mac Keychain; no private key was exported or logged. Only its public half is in Git and the app. Remaining owner actions: approve publication of the signed appcast/archive and corresponding sources; arrange protected signing outside public hosting. Developer ID signing/notarization is separate and can reveal certificate signer identity: inspect final metadata and decide the anonymity/signing tradeoff. No private-key extraction, certificate access, CI-secret registration, Pages publication, push or Release creation is included here. Final archive must be reaudited after signing.

Local verification covers policy parsing, unsafe/missing/upstream keys and feed URLs, fixed release URLs, mandatory signature/automatic/profile flags, unsaved gate and idempotent lazy startup. Official sign_update verified a correct signature and rejected changed payload/wrong signature with the approved dedicated Keychain account. Signed synthetic archive/feed verified offline. Actual Sparkle UI refused file:// transport (the official downloader requires HTTP/HTTPS), displayed a recoverable update error and left the isolated old app unchanged. The task did not weaken TLS or publish a test endpoint. Test transport exceptions were removed from final code. Actual signed feed/download, bad-signature/corruption UI, stage-specific cancel, read-only DMG, successful install/relaunch and native quit cancellation remain unverified; they need a separately approved HTTPS endpoint.

Startup verification: `zsh Scripts/test-startup-updates.sh` uses a URLProtocol stub that intercepts every request, with synthetic XML and isolated temporary UserDefaults. It covers semantic/build ordering, stable archive tags, channels, incompatible macOS versions, invalid XML/DTD/size limits, HTTP/network failures, redirect refusal, real deadline cancellation of a stalled stub, main-actor responsiveness, same-launch and persisted throttling, clock rollback, and cancellation before a manual check. It does not access real feeds, signing keys or archives, or install anything. Live startup feed/UI behavior remains a separate integration check.
